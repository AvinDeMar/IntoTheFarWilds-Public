# Owner-controlled artwork publishing

This repository is independent of development. It has no source-repository webhook, scheduled synchronization, private API access, or automatic artwork importer. Only an explicit owner release request permits publication. A public branch is already public; prepare proposed updates locally or in private staging.

The initial `2026-10-16.1` release is explicitly authorized by the owner. Future releases require a new request, followed by approval of the proposed release after its summary and previews are reviewed.

## Prepare a release

1. Use the installed `$far-wilds-public-art-publishing` Skill, or read its maintained source in `.agents/skills/far-wilds-public-art-publishing/SKILL.md`.
2. Resolve the selected source revision and active approval manifests. Require approved visual masters, canonical IDs/names/order, per-item versions and hashes. Never choose files by newest timestamp or highest version number.
3. Read the source without altering its working tree. Keep the source selection, downloaded masters, prompts, provenance, rights evidence and approval receipt in a separate private staging directory outside this public repository. Hydrate only selected images and verify actual PNG bytes and source hashes.
4. Review provenance and public-display rights for every item. The owner must resolve any third-party rights issue before that item can be published. Approval of artistic quality alone does not establish third-party rights.
5. Write a private selection JSON using the schema below. The public catalog never contains source paths or internal approval evidence.

```sh
python -m pip install -r requirements.txt
python -B scripts/publish_art.py prepare --selection <private-selection.json> --release 2026-10-16.1 --date 2026-10-16
python -B scripts/publish_art.py seal
python -B scripts/publish_art.py verify --expected-icons 201 --private-profile <private-profile.json>
python -B scripts/test_publishing.py
```

`prepare` supports first publication and adding/updating selected batches. Existing entries absent from a batch remain unchanged. Source hashes and a private derivative cache avoid rewriting unchanged images. Repeat the same preparation to confirm no public file or timestamp changes. New release records are created only when the public collection changes.

Inspect the proposed diff and both light/dark composites before publishing. Icon derivatives are **100×80** thumbnails and **400×320** previews: crop the approved 1024-square RGBA master to **(12,112)–(1012,912)**, then resize uniformly with premultiplied-alpha LANCZOS. PNG optimization is lossless; no palette reduction, repainting, or generation is performed. Existing sRGB colors are retained; non-sRGB embedded profiles are converted to sRGB. Personal PNG metadata is dropped. Generic future concept/screenshot artwork keeps its full aspect ratio with bounded previews; it is never forced into icon geometry.

## Private input schema

The external selection file contains `items`. Each item requires:

- `id`, `name`, `display_name`, `version`: canonical identity and approved selection.
- `kind`: `icon` or `artwork`.
- `category`: icons use `resources`/`currencies`; other work uses `concepts`, `characters`, `creatures`, `environments`, `screenshots`, or `illustrations`.
- `group`, `group_slug`, `group_order`, `item_order`: explicit presentation order and stable filesystem grouping. Initial icon groups use resource families 1–27, then currency groups 28–30; members retain their original source order. New groups need unused order values.
- `source_path`, `source_sha256`: a private staged source and its verified hash.
- `approval_status: "Approved"` and `rights_status: "cleared"`: record these only after source approval and provenance/publication checks.

Do not place this input file in the public repository. Do not copy source masters, reference images or approval conversations into public files.

## Review and authorization

Show the owner the selected IDs/versions, proposed additions/replacements/retirements, previews, exact changed files and rights/privacy audit. After explicit release approval, record an external JSON receipt containing:

- `approved: true`, the owner evidence and exact approved release scope.
- `active_ids`: the sorted IDs in the proposed public catalog.
- `catalog_sha256` and `allowlist_sha256`: hashes of the inspected files.
- `diff_sha256`: SHA-256 of UTF-8 JSON generated by `encoded(change_summary())` in the publishing module.

Record actual owner authorization; do not manufacture approval or treat time passing as acceptance. The initial owner request authorizes the initial 201-icon release; later requests require their own release approval.

```sh
python -B scripts/publish_art.py publish --approval <private-approval.json> --private-profile <private-profile.json> --dry-run
python -B scripts/publish_art.py publish --approval <private-approval.json> --private-profile <private-profile.json> --message "Publish owner-authorized artwork release"
```

The publisher verifies the exact catalog, hashes, allowlist and change summary before contacting the remote. It accepts only this independent public repository on `main`, stages only approved changes, and uses a normal push. It never changes source-repository visibility or pushes source history. If a push fails after a local commit, inspect and retry that exact validated commit under the existing authorization; do not replace or force-push history.

## Stable links and retirement

Public filenames use stable canonical IDs. Updated pixels keep the same paths; gallery and website image URLs add a content-hash query to refresh caches only for changed images. Unchanged entries retain their original publication version.

To prepare an explicitly requested retirement, use `retire --ids ID_ONE,ID_TWO --release RELEASE --date YYYY-MM-DD`, then seal, review and obtain release approval as above. Only known catalog derivative paths are removed. Retired IDs remain recorded; their earlier public files can still exist in Git history. Retirement is not a promise of erasure from public clones or caches.

## Website deployment

The static showcase uses only this repository's catalog and public derivatives. There is no private API and no application framework.

```sh
python -B scripts/publish_art.py build-site --output <new-external-build-directory>
gh workflow run deploy-gallery.yml --ref main
```

The Pages workflow is **manual (`workflow_dispatch`) only**. Pushes and source changes do not trigger it. Configure GitHub Pages with the GitHub Actions build type. Deploy only after release authorization, then check its actual public URL without authentication. No paid services are provisioned.

## Publication allowlist

`publication-allowlist.json` records the exact public file set and SHA-256 hashes; its own path is explicitly declared without a circular self-hash. It is derived from a fixed implementation/document list plus catalog derivative and release-record paths. Unexpected files or symlinks stop preparation verification. A separate private profile can supply additional forbidden strings for privacy scanning.

Before pushing, inspect the staged paths and diff. Confirm no masters, generator sources, prompts, private documents/history, local filesystem paths, reference photography, credentials, Unreal/Blender assets or unlicensed third-party art appear. Ordinary Git PNG blobs are required; no LFS dependency is needed by visitors.

After publication, verify remote commit/tree identity, public file hashes, all image links, rendered labels/navigation, and unauthenticated access. Report the release, catalog counts, rights/provenance result, repository size, public gallery/Pages URLs, and any remaining setup limitation.
